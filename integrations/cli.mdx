`relaymessenger` is the local process that connects an engine on your computer to
a Relay conversation. It is shared by every
[coding agent integration](/integrations).

```bash
npm install -g @relaymessenger/Relay-CLI
relaymessenger pair
```

## Pairing

Pairing is a device-code flow:

<Steps>
  <Step title="The CLI creates a pairing">
    It creates a short-lived pairing and long-polls it with a poll token.
  </Step>
  <Step title="You claim it in Relay">
    Claiming creates a Relay agent owned by your account.
  </Step>
  <Step title="Relay returns the token">
    The Agent Token goes only to the waiting CLI.
  </Step>
  <Step title="The CLI pins the owner">
    It stores the token with owner-only permissions and records the owner user id
    returned by `GET /v1/agents/me`.
  </Step>
</Steps>

Pairing pins your Relay user id as the only default sender allowed to drive the
agent.

## What Relay never receives

<Warning>
Relay never receives your engine provider keys, SSH keys, or full parent process
environment.
</Warning>

ACP subprocesses receive only platform basics, the engine and provider variables
for the supported engines, and variables you add explicitly through
`RELAYMESSENGER_ENGINE_ENV`.

## Approval and delivery safety

| Guarantee | What it prevents |
| --- | --- |
| Only the pinned owner can create prompts or answer approval cards | A non-owner message is dropped before its content is interpreted |
| Each approval is a create-once file on disk | A replayed approval cannot run twice |
| The exact operation must fit in the security preview | Incomplete or oversized operations are denied instead of blindly allowed |
| The event cursor advances in the same atomic write as the pending queue | A crash cannot acknowledge an event that was never recorded |
| Agent and tool turns are at-most-once | A crash cannot silently repeat a deploy, deletion, command, or external send |
| Completed replies use an on-disk outbox and a stable idempotency key | Delivery retries without rerunning the agent turn |

<Warning>
Event long-polling is exclusive per Agent Token and mutually exclusive with
webhooks. Give every active consumer its own Relay agent and token.
</Warning>

## Diagnose

```bash
relaymessenger doctor
```

`doctor` verifies Node, pairing and owner pinning, token permissions, API
reachability, saved state, the exact Claude and Codex adapter entrypoints, and
the installed Hermes binary and readiness check.

See [integration troubleshooting](/integrations/troubleshooting) for what each
red line means.

## Local files

```text
~/.relaymessenger/config.json                        paired token, origin, owner (0600)
~/.relaymessenger/codex-notify.json                  project roots opted into Codex notify
~/.relaymessenger/accounts/<identity>/state.json     saved cursor, queue, outbox
~/.relaymessenger/accounts/<identity>/approvals/     one file per approval
~/.relaymessenger/accounts/<identity>/sessions.json  conversation to ACP sessions
~/.relaymessenger/accounts/<identity>/mcp-sends/     Codex MCP logical sends, one file each
~/.relaymessenger/accounts/<identity>/installed-plugins/ stable plugin copies
```
