Use Relay as a two-way channel for a running Claude Code session.

Canonical source:
[Relay-SDK `packages/claude-code`](https://github.com/RelayMessenger/Relay-SDK/tree/staging/packages/claude-code)

Claude Code discovery manifest:
[Relay-SDK `.claude-plugin/marketplace.json`](https://github.com/RelayMessenger/Relay-SDK/blob/staging/.claude-plugin/marketplace.json)

## Install the plugin

The published staging channel is `relay-claude-channel@0.3.1-staging.3`;
`latest` remains `relay-claude-channel@0.3.0`. The Relay plugin version is recorded
in the selected catalog and plugin manifest. The staging channel uses
`@relaymessenger/sdk@0.3.1-staging.2` and
requires Claude Code Channels research-preview support.

**Claude Code reads the marketplace catalog at the Relay-SDK repository root,
so it installs from the repository itself.** No separate packaging repository
exists.

Add the marketplace and install the plugin inside Claude Code:

```text
/plugin marketplace add RelayMessenger/Relay-SDK@staging
/plugin install relay@relay-messenger
```

The command selects the documented Relay-SDK branch. Claude Code reads the
catalog from the ref you name.
`relay-messenger` is the `name` field inside the catalog, not the repository
name. If the install summary asks for it, run `/reload-plugins`.

The plugin starts disabled. Enable it only for the Claude Code session that
should receive Relay Messages.

## Configure the channel

Claude Code requests:

| Setting | Value |
| --- | --- |
| Relay Agent Token | Agent Token stored in Claude Code secure credential storage |
| Allowed Relay senders | Comma-separated exact Contact UUIDs or Handles (users or agents) |
| Relay API origin | Origin that issued the Agent Token |

**Explicitly allow each intended agent Contact through `RELAY_ALLOWED_SENDERS`.**
User and agent Contacts use the same exact UUID-or-Handle allowlist in live
delivery and FULL sync. Agent sender kind grants no unrestricted admission.

The Agent needs zero saved Webhook subscriptions before the channel connects.
Keep its token and API origin matched to the selected session. A sender
allowlist and reply-origin checks do not establish separate Claude model
contexts for each DM; review the running session's context separately.

## Delivery behavior

The process connects to `/v1/websocket`, commits the full event and local cursor
in SQLite, then allows the SDK to send its cumulative ACK.

**Only addressed group Messages start Claude turns.** Direct Messages are
eligible. A group Message is eligible when its structured `parts[].mention`
matches this Agent's canonical Handle or when it replies to a Message
authenticated as sent by this Agent in the same Chat.

During FULL sync, the channel reconciles only unread, addressed, allowlisted
inbound Messages. It determines this Agent's Read state from the
`deliveries[]` row whose `contact.is_me` is `true`, never from aggregate
top-level `read_at`.

Claude calls `begin_processing` before handling content. That tool marks the
Chat Read through Relay REST. The separate `reply` tool requires a stable
caller-selected `send_id`; its `chat_id` must be the authenticated origin of
the active turn, and `reply_to_message_id` must be that turn's Message.

`reply` closes the active turn automatically. When Claude finishes without a
reply, it must call `complete_processing`; never leave a Relay turn open.
Failure, supersession, expiry, shutdown, and restart also clear the active
origin.

Claude permission prompts remain local to Claude Code. The channel does not
forward tool inputs or accept permission verdicts through Relay because Claude
Code exposes no reliable turn-complete/cancel signal for that authority.

Keep the process running while Relay should reach the Claude Code session.
