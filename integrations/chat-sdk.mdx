Connect Chat SDK to Relay and answer messages from an HTTP handler.

## Before you start

You need Node.js 22.22.3 or newer, an Agent Token, and a public HTTPS route for the webhook. Set `RELAY_API_URL` to `https://api.staging.relayapp.im`, the API the token comes from. [Create a webhook subscription](/events/webhooks/subscriptions) for that route and keep its one-time signing secret as `RELAY_WEBHOOK_SECRET`. Install Chat SDK, its in-memory state, and the Relay adapter, all from the same major version line:

```bash
npm install chat@4.39.0 @chat-adapter/state-memory@4.39.0 \
  @relaymessenger/chat-sdk-adapter@staging
```

The adapter's source is [packages/chat-sdk-adapter](https://github.com/RelayMessenger/Relay-SDK/tree/staging/packages/chat-sdk-adapter). For a standalone Node HTTP server instead of a framework route, start from its [server example](https://github.com/RelayMessenger/Relay-SDK/blob/staging/packages/chat-sdk-adapter/examples/server.mjs).

## Connect

Create one Chat SDK instance with the Relay adapter and register a direct-message handler. Three adapter settings matter. `burst` waits two seconds and then runs the handler once for the latest message. `markReadOnReceipt` marks the chat read as soon as the signature checks. `abortActiveTurnOnReceipt` lets a newer message cancel a running turn through `thread.signal`, so pass that signal to your model call. Mount `POST` at the route you registered:

```typescript
import { Chat } from "chat";
import { createMemoryState } from "@chat-adapter/state-memory";
import { createRelayAdapter } from "@relaymessenger/chat-sdk-adapter";

const chat = new Chat({
  userName: "Relay example",
  concurrency: { strategy: "burst", debounceMs: 2000 },
  adapters: {
    relay: createRelayAdapter({
      baseUrl: process.env.RELAY_API_URL!,
      token: process.env.RELAY_AGENT_TOKEN,
      webhookSecret: process.env.RELAY_WEBHOOK_SECRET,
      markReadOnReceipt: true,
      abortActiveTurnOnReceipt: true,
    }),
  },
  state: createMemoryState(),
});

chat.onDirectMessage(async (thread, message) => {
  await thread.post(`Echo: ${message.text}`);
});

export async function POST(request: Request): Promise<Response> {
  return chat.webhooks.relay(request);
}
```

Pass the request to the adapter with its body unchanged; the signature is over the raw bytes. In-memory state is for local work; swap it for a shared store before more than one instance runs.

## Send it a message

Open Relay on your phone and send a message to your agent's handle. Relay posts the event to your route, the adapter verifies it, and your handler runs. The echo comes back in the same chat. To watch the exchange from a terminal, run `npx relaymessenger@staging watch @<handle>`.

## What it can do

The adapter gives your handler the Relay features below; the rest of the API is one import away.

| Relay feature | Chat SDK adapter |
| --- | --- |
| Wakes when a message arrives | Yes, by webhook. |
| Reply in the chat | Yes, with a send key derived from the event id and the send ordinal, so a retry never sends twice. |
| Send attachments | Yes, from a public HTTPS URL or from file bytes; see [attachments](/concepts/messages/attachments). |
| Read chat history | Yes. The adapter walks a chat's history backward, 100 messages a page. |
| Second message during a reply | Waits or cancels the running turn, by the three settings above. |

Chat SDK's default `concurrency` is `drop`: a message that arrives during a running handler throws a `LockError`, the webhook fails, and Relay [retries the delivery](/events/webhooks/delivery). The `burst` setting replaces that. Earlier messages in a burst arrive in `context.skipped`; join them when one reply should cover the whole burst. A send outside a webhook turn needs your own `idempotencyKeyResolver` from a stable task identity, and an empty response sends no message.

## When it fails

If signature verification fails, the secret is not the one from this subscription or the body was re-encoded before the adapter saw it. If no reply comes, read the handler's logs; the turn either threw or never started. If a send's result is uncertain, retry it with the same idempotency key and the same content, and keep the prepared attachment id rather than allocating a new one.
