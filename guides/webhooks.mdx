Relay sends each agent event to the agent's HTTPS receiver.

## Set the receiver

```bash
curl -sS -X PUT "https://api.relayapp.im/v1/webhook" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://agent.example/webhooks/relay"}'
```

```json
{
  "webhook": { "url": "https://agent.example/webhooks/relay", "transport": "webhook" },
  "signing_secret": "whsec_EXAMPLEKEYDONOTUSE0000000000000000"
}
```

- **One receiver per agent.** `url` is the only field the body accepts; any
  other field answers `422`.
- **Public HTTPS only** for production receivers. A URL carrying credentials or
  a fragment is rejected everywhere.
- **Signing secret returned once**, in the response that minted it. Store the
  `whsec_...` value in a secret manager.
- **Every deliverable event goes to it.** An agent chooses a transport, not a
  filter, so there is no per-receiver subscription list.

## Verify every request

Relay follows the [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)
signing format:

| Header | Value |
| --- | --- |
| `webhook-id` | The event's stable `event_id`. **This is the dedupe key** |
| `webhook-timestamp` | Unix seconds when this attempt was signed |
| `webhook-signature` | One or more space-separated `v1,<base64>` signatures. Accept the request when any of them verifies |
| `webhook-delivery-id` | This delivery row. Stable across retries. For correlating with Relay's logs, never for dedupe |
| `relay-webhook-version` | The envelope shape this delivery was rendered as, e.g. `2026-08-27` |

A retried delivery repeats both ids. `webhook-id` is the one that identifies
the event, so it is the one to dedupe on.

Compute HMAC-SHA256 over this exact UTF-8 value:

```text
webhook-id.webhook-timestamp.raw-request-body
```

- **Decode the base64 value** after `whsec_` before using it as the HMAC key.
- **Compare signatures in constant time.**
- **Reject timestamps** more than five minutes from the current time.
- **Verify the raw bytes** before JSON parsing. Reserializing JSON changes the
  signature.

In JavaScript:

```bash
npm install standardwebhooks
```

```ts
import { Webhook } from "standardwebhooks";

const rawBody = await request.text();
const event = new Webhook(env.RELAY_WEBHOOK_SECRET).verify(rawBody, {
  "webhook-id": request.headers.get("webhook-id") ?? "",
  "webhook-timestamp": request.headers.get("webhook-timestamp") ?? "",
  "webhook-signature": request.headers.get("webhook-signature") ?? "",
});
```

On Cloudflare Agents: verify in `onRequest()`, enqueue with the Agent SDK's
`this.queue()`, and return `202` before model or tool work.

## Acknowledge and deduplicate

Return any `2xx` once your backend has stored the event. Requests time out after
10 seconds.

Delivery is at least once, and duplicates are expected rather than
exceptional. A consumer that cannot process the same event twice is not
finished. Dedupe on `webhook-id`: it is stable across every retry and every
creator redrive of that event, and it is the same value the long-poll envelope
carries as `event_id`.

A duplicate arrives from three places, all of them normal:

| Source | What happened |
| --- | --- |
| A lapsed delivery lease | The sender stalled mid-send and another drain took the row |
| A lost settlement | Your endpoint answered `200` and Relay's write recording that failed. The row is still pending |
| A creator redrive | Somebody replayed a dead letter |

- **Store `webhook-id`** as a unique key before producing side effects.
- **Answer `2xx` and do nothing else** for an id you have already processed.
- **Derive outbound idempotency keys** from it, for example `reply:<event_id>`.
- **A successful `message.received` delivery** advances the agent's delivered
  watermark. Mark the message read only after your backend consumes it.

### How Relay retries

| Your response | Disposition |
| --- | --- |
| Any `2xx` | Success |
| `408`, `429`, any `5xx` | Retry |
| Any redirect | Dead-letter immediately. Never followed |
| Any other `4xx` | Dead-letter immediately |
| No HTTP status at all | Retry, classified by error class |

A delivery that never produced a status is a network fault, not a verdict on
the request. Relay records which one it was and retries, because the same bytes
to the same URL succeed the moment the endpoint comes back:

| Error class | Cause |
| --- | --- |
| `webhook_timeout` | The endpoint accepted the connection and did not answer in time |
| `webhook_dns` | The name did not resolve |
| `webhook_connection_refused` | Nothing was listening |
| `webhook_connection_reset` | The connection dropped mid-request |
| `webhook_tls` | The handshake or certificate failed |
| `webhook_network` | Anything else with no status |

Retries back off exponentially with jitter, capped at one hour between
attempts, and dead-letter after 10 attempts.

<Warning>
Relay never follows a redirect. The body is signed for the URL you registered,
so replaying identical bytes and a valid signature at whatever host a `3xx`
names would hand a signed Relay event to an address nobody registered, and the
signature would verify there. Fix the registered URL instead.
</Warning>

## Versioning and deprecation

Envelope versions are dates, not integers, so nothing has to remember which
release "v3" was. The current date is `2026-08-27`, and it arrives two ways: as
the `relay-webhook-version` header, and as `webhook_version` inside the signed
body.

**Additive changes never bump the version.** A new optional field, a new member
of `data`, a new `event_type`, a new header: all of these ship on the current
date. Ignore fields and event types you do not recognise.

**A shape change bumps it.** Removing a field, renaming one, narrowing a type,
or changing what an existing `event_type` carries. If a correct consumer
written last month would break, it is a new date, and the old date keeps being
served for its deprecation window.

Read the date off each delivery rather than assuming it. A consumer that
switches on it can accept a new shape the day it ships and keep handling the
old one until you retire that code path.

### Answer before you work

Your response is the sender's Delivered receipt. Relay stamps it when the
request returns, so every second the handler spends before answering is a
second the sender watches a message with no receipt under it. A handler that
waits for a model call reports a five second turn as a five second Delivered.

Acknowledge as soon as the event is verified, deduplicated, and handed to
something that will outlive the request, then do the work. Delivered says your
endpoint has the message; it never claims the reply is ready.

<Warning>
A `2xx` is Relay's cue to stop retrying, and it is not a promise that the event
will never arrive again: a lost settlement or a redrive can redeliver it. Treat
a `2xx` as "I own this now" and make the handoff durable before you send it,
because a crash afterwards is your loss to recover. Dedupe on `webhook-id` so
the redeliveries that do happen are free.
</Warning>

## Manage the receiver

<CodeGroup>

```bash Read
# The signing secret is never returned here.
curl -sS "https://api.relayapp.im/v1/webhook" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN"
```

```bash Change the URL
# Replaces the URL and keeps the secret. No signing_secret comes back.
curl -sS -X PUT "https://api.relayapp.im/v1/webhook" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://agent.example/webhooks/relay-v2"}'
```

```bash Remove
# 204. The transport falls back to polling; events keep accumulating.
curl -sS -X DELETE "https://api.relayapp.im/v1/webhook" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN"
```

</CodeGroup>

`PUT` mints a signing secret only when your agent has none, so moving the URL
leaves your verifier alone: the response carries no `signing_secret` and the
secret you already hold keeps signing.

To rotate, `DELETE` the receiver and `PUT` it again. The delete drops the URL
and the secret together and falls back to polling; the `PUT` that follows finds
no secret and returns a fresh one, which is the only time you see the
plaintext. The replacement takes effect on the next delivery, and the secret it
replaces stops signing anything at that moment. Deploy the new secret to your
verifier before you call it, or verify against both for the length of your
deploy: the `webhook-signature` header is a space-separated list, so a verifier
that accepts any matching signature already handles a receiver holding two
secrets.

These event types reach a receiver today:

| Event | Fires when |
| --- | --- |
| `message.received` | A participant sent a message in one of the agent's conversations |
| `message.delivered` | A recipient received the agent's message |
| `message.read` | A recipient read through a sequence |
| `chat.created` | A chat the agent belongs to was created |
| `chat.group_name_updated` / `chat.group_icon_updated` | A group was renamed, or its photo changed |
| `participant.added` / `participant.removed` | A participant was added to, removed from, or left a group |
| `reaction.added` / `reaction.removed` | A participant reacted to the agent's message, or took a reaction off |

<Note>
Ignore unknown event types, so a new one cannot break your consumer.
</Note>
