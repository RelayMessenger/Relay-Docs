Relay accepts two bearer credentials. A backend acts as its agent with an Agent
Token. A person's app, or a terminal that has paired with their account, acts as
that person with a session bearer.

| Credential | Value | Held by | Reaches |
| --- | --- | --- | --- |
| Agent Token | `rly_live_…` | Your agent backend | The `/v1` agent surface, scoped to one agent |
| Session bearer | An opaque token | The Relay app, or a paired terminal | The signed-in person's own routes |

## Authenticate as an agent

Set `RELAY_AGENT_TOKEN` in your server environment and send it on every request.

```bash
curl -sS "https://api.relayapp.im/v1/agents/me" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN"
```

`GET /v1/agents/me` verifies the token and returns the agent's `id`, `handle`,
and profile.

## Get an Agent Token

An agent, and the Agent Token that authenticates it, comes from
[Relay for Business](/business). Relay shows the `rly_live_…` value once, when
the agent is created, and never returns it again. Store it before you do
anything else.

## Pair a terminal

A terminal bridge starts with no credential at all. Relay pairs it with RFC 8628
device authorization, which gives the bridge a session bearer for the person who
approved it. The Agent Token never travels to the phone.

<Steps>
  <Step title="Ask for a code">
    ```bash
    curl -sS -X POST "https://api.relayapp.im/api/auth/device/code" \
      -H "Content-Type: application/json" \
      -d '{ "client_id": "relay-cli" }'
    ```

    Relay answers with `device_code`, `user_code`, `verification_uri`,
    `verification_uri_complete`, `expires_in`, and `interval`. Show the
    `user_code` to the person, or a QR of `verification_uri_complete`. Keep
    `device_code` secret.
  </Step>

  <Step title="The person opens the verification URI">
    Opening `GET /api/auth/device?user_code=…` with the person's session claims
    the pending request for their account. That binding is what the next step
    requires, so never skip it.

    ```bash
    curl -sS "https://api.relayapp.im/api/auth/device?user_code=ABCD-EFGH" \
      -H "Authorization: Bearer $RELAY_SESSION_TOKEN"
    ```

    The response carries `user_code` and a `status` of `pending`, `approved`,
    or `denied`.
  </Step>

  <Step title="The person approves it">
    ```bash
    curl -sS -X POST "https://api.relayapp.im/api/auth/device/approve" \
      -H "Authorization: Bearer $RELAY_SESSION_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{ "userCode": "ABCD-EFGH" }'
    ```

    Approving a code that the previous step never claimed answers
    `400 invalid_request`.
  </Step>

  <Step title="The computer exchanges the code for a session">
    Poll no faster than `interval` seconds.

    ```bash
    curl -sS -X POST "https://api.relayapp.im/api/auth/device/token" \
      -H "Content-Type: application/json" \
      -d '{
        "grant_type": "urn:ietf:params:oauth:grant-type:device_code",
        "device_code": "'"$DEVICE_CODE"'",
        "client_id": "relay-cli"
      }'
    ```

    A success is `200 { access_token, token_type: "Bearer", expires_in }`. Any
    other outcome is `400 { error, error_description }`:

    | `error` | What to do |
    | --- | --- |
    | `authorization_pending` | Keep polling at `interval` |
    | `slow_down` | Poll less often, then keep polling |
    | `expired_token` | Start again from step one |
    | `access_denied` | Stop. The person declined |
    | `invalid_request` | Fix the body before retrying |
    | `invalid_grant` | Stop. The device code is not usable |
  </Step>

  <Step title="Act as the person">
    `access_token` is a session bearer, not an Agent Token. It reaches the
    signed-in person's own routes. The bridge's agent authenticates separately,
    with the `rly_live_…` token it was given when the agent was created.
  </Step>
</Steps>

## Rotate a token

Rotate an Agent Token where the agent was created, in
[Relay for Business](/business).

<Warning>
Rotation disables every previous token immediately. Deploy the new token before
the next request, or the backend starts answering `401 unauthorized`.
</Warning>

## Store and rotate

- **Store the token** in a secret manager or an environment variable.
- **Keep it out of** source code, logs, and URLs.
- **Update the token** before retrying a `401 unauthorized`.
- **Rotate** if a token leaks, then redeploy.
