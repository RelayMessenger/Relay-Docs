An `invoice` part is a card that asks the person to pay. It shows your business name, an amount, and a title; tapping it opens your own checkout link. Relay never touches the money: there is no Relay Stripe account, no processing step, and no Relay fee. You get paid the way you already get paid; Relay only carries the card and tells you, through the status you set, when the person finishes.

## Send an invoice

An `invoice` part carries a `title`, an integer `amount` in minor currency units, a `currency`, whether the goods are `physical` or `digital`, and the `url` your own checkout opens. Only an agent can send an invoice, and it must be the only part in its Message. Tap the card in the demo to see the checkout open; the demo loads nothing from the example URL.

### Fields

- Only an agent can send an invoice; a person's attempt fails.
- A Message carries at most one `invoice` part, and it must be the Message's only part: no text, media, buttons, or selection beside it.
- `title` is 1 to 32 characters after surrounding whitespace is trimmed.
- `amount` is an integer number of minor currency units from 1 to 99,999,999 (Stripe's own ceiling).
- `currency` is a 3-letter ISO code, case-insensitive in, always returned lowercase.
- `goods` is `physical` or `digital`; see [Physical and digital](#physical-and-digital).
- `url` is the `https` link to your own checkout, up to 2048 characters, with a host and no username or password (`https://buy.stripe.com@evil.com` is `evil.com`, and is refused). Relay stores it normalized, so a mixed-case scheme or missing trailing slash comes back the way Relay wrote it, not the way you sent it.
- `recurring` is optional; see [Subscriptions](#subscriptions).
- Unknown fields are rejected.

## Physical and digital

What the card does when it's tapped depends on `goods` and, for digital goods, the App Store storefront the person's device last reported:

| Goods | Storefront | What happens |
| --- | --- | --- |
| `physical` | Any | The card opens your checkout `url` in the app's own in-app browser. |
| `digital` | US App Store | The card opens your checkout `url` in Safari, outside the app. |
| `digital` | Any other App Store | The invoice is rejected when you send it. The card is never created. |

<InvoicePreview agent="Nimbus Cloud" title="Pro plan" amount={1900} currency="usd" goods="digital" payable={false} />

Relay checks the storefront the person's device last reported, not their location, and reads it through StoreKit rather than Location Services. A device that has never reported a storefront is let through; that is App Store review's backstop to enforce, not Relay's. This follows Apple App Store Review Guideline 3.1.3(e) (goods and services outside the app for physical purchases) and 3.1.1(a) (in-app purchase for digital goods and services).

## Subscriptions

Add `recurring` to bill on a schedule: an `interval` of `day`, `week`, `month`, or `year`, and an optional `interval_count` (default `1`) to bill every few of them, such as every 2 weeks or every 3 months. The span of `interval` × `interval_count` cannot exceed 3 years. The card shows the amount with its cadence, for example "$19.00/month".

<InvoicePreview agent="Nimbus Cloud" title="Pro plan" amount={1900} currency="usd" goods="digital" recurring={{ interval: "month" }} url="https://buy.stripe.com/sub_123" />

Relay does not run the subscription. Your own checkout link and your own billing system own the recurring charge, the retries, and the renewal; call [Mark it paid](#mark-it-paid) from your billing webhook on every charge so the card in Relay stays current.

## Mark it paid

Move the card's `status` with `PUT /v1/messages/{message_id}/invoice`. Only the agent that sent the invoice can call this; every other identity gets a `403`. Any status is valid from any other status, and setting the status it already has is a no-op that still returns `200`.

| `status` | What the card shows |
| --- | --- |
| `requested` | The card as sent: tappable, no caption. This is the default when you never call this route. |
| `succeeded` | "Paid". The card stops opening the checkout. |
| `canceled` | "Canceled". |
| `expired` | "Expired". |
| `refunded` | "Refunded". |

<InvoicePreview agent="Sonic Coffee" title="House blend, 250 g" amount={2400} currency="usd" goods="physical" status="Paid" />

Call this from your own payment provider's webhook (Stripe, or whichever processor your checkout `url` uses), not from guesswork about whether the person paid.

<CodeGroup>
```typescript TypeScript SDK
import Relay from "@relaymessenger/sdk";

const relay = new Relay({
  apiKey: process.env.RELAY_AGENT_TOKEN!,
  baseURL: "https://api.staging.relayapp.im",
});

await relay.messages.invoice.update(messageId, { status: "succeeded" });
```

```bash HTTPS
curl -sS -X PUT "https://api.staging.relayapp.im/v1/messages/$MESSAGE_ID/invoice" \
  -H "Authorization: Bearer $RELAY_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"status":"succeeded"}'
```
</CodeGroup>

```http
HTTP/1.1 200 OK
```

A real status change pushes a `message.upserted` for the card to every person in the chat; a no-op pushes nothing. There is no separate webhook for this, since you are the one who called it, so you already know.

## Send one from a runtime

Invoices are a property of the Message, so every runtime sends them through the send path it already has: a backend includes the `invoice` part alone in `parts`; a runtime with a send tool takes an `invoice` argument; and a runtime that answers in text ends its answer with a fenced code block tagged `invoice` holding the fields, which the bridge lifts out into its own solo Message. Any words before the fence go out first, as an ordinary text Message, since an invoice cannot share a Message with anything else. Sending more than one invoice fence, or an invoice fence alongside a `buttons` or `selection` fence, in the same answer is an error.

## Only people pay

- Only an agent can send an invoice.
- Only a person can react to an invoice; an agent's reaction is rejected.
- Only the agent that sent an invoice can move its status; every other identity, including another agent in the same chat, is rejected.
- Invoices work in direct and group chats the same as any other part.
- Replies to an invoice Message are ordinary replies; an invoice has no reply format of its own.

## When it fails

| Status | Code | Cause |
| --- | --- | --- |
| `400` | [1005](/api-reference/errors#1005) | The invoice is not alone in its Message, `title`/`amount`/`currency`/`goods` fails validation, `url` is not `https`, has no host, or carries a username or password, `recurring`'s span exceeds 3 years, or the status route's `status` is not one of the five known values. |
| `403` | [2003](/api-reference/errors#2003) | A person sent an invoice, an agent reacted to one, or an identity other than the sending agent called the status route. |
| `404` | [2001](/api-reference/errors#2001) | The status route's message does not exist, is not visible to the caller, or carries no invoice part. |
| `422` | [2006](/api-reference/errors#2006) | A digital invoice would go to a person whose device last reported a non-US App Store storefront. |
