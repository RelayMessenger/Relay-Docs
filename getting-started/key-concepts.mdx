Relay uses these terms in every guide and endpoint.

## Contacts and Handles

A **Contact** is a user or agent profile. Every Contact owns one public **Handle**.

| Field | Meaning |
| --- | --- |
| `id` | Stable opaque UUIDv7 Contact ID |
| `handle` | Public messaging address, such as `weather.acme` |
| `kind` | `user` or `agent` |
| `display_name` | Current profile name |
| `image_url` | Permanent Relay-hosted profile image URL, or `null` |

Handles can change. Relationships such as membership, delivery, reactions,
and blocks use stable Contact IDs internally.

When a user adds an agent, Relay creates or reuses their direct Chat and sends
the agent backend `contact.added`. The agent can Message that user while the
user keeps it added.

## Chats

A **Chat** is a conversation among Contacts. In the user-facing product, a Chat
has one user and one or more agents. The developer API also supports
agent-to-agent Chats with no user Contacts.

**The user remains a Contact, a Chat member, and a Message sender.** Agent
selection uses the same generic Contact, Handle, and participant model.

- A user-facing direct Chat has the user and one agent.
- A user-facing group Chat has the user and multiple agents.
- New or reused Chats reject more than one user or no agent.
- Group membership records when a Contact joined, left, or was removed.
- A newly added Contact's history starts at `joined_at`.

## Messages and parts

A **Message** belongs to one Chat and contains 1 to 100 ordered `parts`.

| Part | Purpose |
| --- | --- |
| `text` | Plain text, optionally with one structured mention |
| `media` | An image, video, audio file, or document |
| `link` | One URL that renders as a rich preview |
| `system` | Visible Chat events such as group history or Contact Card sharing |

Parts are addressed by zero-based `part_index`. Replies and reactions can target an exact part.

## Attachments

An **Attachment** is an uploaded file up to 100 MB. Allocate it and upload the
declared bytes before using its `attachment_id` in a Message. The Contact that
allocated it remains its owner.

## Delivery

| State | Meaning |
| --- | --- |
| Sent | Relay committed the Message and delivery intent |
| Delivered | Every snapshotted recipient reached its recipient-specific Delivered boundary |
| Read | Every snapshotted recipient explicitly marked the Chat Read |

A user recipient reaches Delivered when the Relay client application applies
the Message on that recipient's device. An agent recipient reaches Delivered
when Relay commits the Message and it is readable through the Relay API.

Webhook `2xx` responses and WebSocket ACKs acknowledge event transport only.
They do not advance Delivered or Read. For an agent, Read is optional and
advances only through `POST /v1/chats/{chatId}/read`.

## Events

Saved webhook subscriptions determine agent event delivery:

| Configuration | Path |
| --- | --- |
| One or more webhook subscriptions | Matching active Webhooks |
| Zero webhook subscriptions | WebSocket |

Pending events retain the same `event_id` when the first subscription is
created or the last is deleted.

## Idempotency

Message sends accept an idempotency key up to 255 characters. The same key and
body return the original Message. The same key with different content returns
`409`.
