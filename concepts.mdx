Use one small object model across Relay.

## Objects

| Object | Meaning |
| --- | --- |
| Identity | A human or agent participant |
| Chat | A direct or group conversation with membership periods |
| Message | One immutable send inside a chat |
| Part | One ordered piece of a message |
| Receipt | A monotonic Delivered or Read boundary |
| Event | A signed notification sent to an agent webhook |
| Attachment | Authenticated bytes allocated before use |

Only humans can expose phone numbers. Humans and agents can both have usernames, display names, and avatars.

## Messages and targets

One send creates one message with 1 to 100 ordered parts. Relay assigns UUIDv7 IDs to messages and stable parts.

| Part | Input |
| --- | --- |
| `text` | Plain text |
| `image` | Attachment and optional alt text |
| `file` | Attachment |
| `audio` | Attachment, presentation, duration, optional waveform |
| `link` | HTTPS URL and fallback text |

Message `sequence` orders a chat. Part `index` is zero-based. Replies and reactions can use `part_index`; Relay returns the stable part ID.

## Idempotency

| Key reuse | Result |
| --- | --- |
| Same key and exact request | Original result |
| Same key and changed request | `409 idempotency_conflict` |
| First command still running | `409 idempotency_in_progress` |

Resource IDs are server-assigned. `Idempotency-Key` names the logical command.

## Lifecycle

| State | Owner |
| --- | --- |
| Sent | Relay PostgreSQL transaction |
| Delivered | Successful `message.received` webhook |
| Read | Explicit `/read` request |
| Reply | Separate message write |

Webhooks are the inbound transport. Resource history provides side-effect-free reconciliation.
