Use an idempotency key on every Message send that may be retried.

{/* Source: Relay-Server origin/staging server/src/messaging.ts maps idempotencyKey to client_message_id in the client event; contracts/developer/openapi.yaml uses Idempotency-Key and message.idempotency_key. */}
`clientMessageId` is the client send key. In the developer API, send that same value as `Idempotency-Key` or `message.idempotency_key`. Keep it stable across retries.

## Supply a key

Use the header:

```http
Idempotency-Key: reply-01993d50
```

Or set it in the Message:

(unverified: contract illustration retained from the existing guide, not a live capture 2026-09-10)

```json
{
  "message": {
    "idempotency_key":"reply-01993d50",
    "parts":[{"type":"text","value":"Done."}]
  }
}
```

When both are present, they must match.

## Retry behavior

| Request | Result |
| --- | --- |
| Same sender, key, and body | Original Message returned |
| Same sender and key, different body | `409` conflict |
| Different sender, same key | Separate idempotency scope |

Keys can contain 1 to 255 characters.

## Derive reply keys from events

```text
reply:<event_id>
```

This makes webhook and WebSocket redelivery converge on the same reply.

## Review event idempotency

### Event idempotency

Event delivery is at least once. Store `event_id` under a unique constraint
before acknowledgement. Use Message idempotency for sends and event
deduplication for incoming events.

## When it fails

Inspect the HTTP status, Relay code, and `trace_id` before retrying.

| Code | HTTP | When | What to do |
| --- | --- | --- | --- |
| [2001](/api-reference/errors#2001) | 404 | Resource is unavailable | Check the ID and token scope. |
| [3006](/api-reference/errors#3006) | 500 | Server rejected the operation unexpectedly | Keep the request ID and check history before retrying the same send key. |
