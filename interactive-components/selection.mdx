Send a question with a `selection` part to collect several choices in one reply.

## Send a selection

This request contains a required nonblank `text` part followed by a `selection` part. The preview shows the same question and options, in the same order. Try toggling choices, **Clear**, and **Send**; this demo stays in your browser and sends no request.

The send path returns `202` after storing the message. Keep the returned message ID so your application can associate responses with this question. Reuse the same request and idempotency key after an uncertain send.

### Choose and submit

The app starts with empty choices. Toggling a choice stages it locally; **Clear** empties the selection. **Send** becomes available when at least one choice is selected and submits one reply.

While a submission is pending, the choices stay fixed. Acceptance removes the choice controls and leaves the question plus the person's ordinary text reply. A failed attempt retains the choices and retries the same logical operation.

Selection inherits existing Chat membership rules: a Chat supports at most one human user, with multiple agents allowed. The human user submits the response; agents send prompts and receive responses.

Read responses expose `has_responded` on the prompt part. This read-only flag reflects the authenticated viewer's durable response claim, shared across that user's devices and idempotency keys. A group response follows the chat's normal recipient visibility.

## Receive stable values

The user's submission contains exactly two ordered parts: readable text, then structured metadata. Its `reply_to` identifies the source message and selection part.

  <Tab title="What you receive">

    ```json
        "parts": [
          {"type":"text","value":"Research, Design"},
          {"type":"selection_response","selected_values":["research","design"]}
        ],
        "reply_to": {
          "message_id":"01993d50-ef7b-7b37-886b-23fd80c7ec13",
          "part_index":1
        }
      }
    }
    ```
  </Tab>

The event example shows the response fields used by your handler. The preview displays exactly the text part, **Research, Design**; metadata adds no visible text.

The text equals the selected source labels joined with `, `, in source-option order. It supplies the readable bubble and notification text. The `selection_response` part carries metadata only.

Your existing signed [webhook](/webhooks/verify-signatures) or [WebSocket](/websocket/index) handler receives the ordinary `message.received` event. The SDK's default event types expose the metadata:

```typescript Application handler
import type { RelayWebhookEvent } from "@relaymessenger/sdk";

function selectionFrom(event: RelayWebhookEvent) {
  if (event.event_type !== "message.received") return;
  const response = event.data.parts.find(
    (part) => part.type === "selection_response",
  );
  if (!response || !event.data.reply_to) return;
  return {
    source: event.data.reply_to,
    selectedValues: response.selected_values,
  };
}
```

Dispatch your own application handler using the source message ID, part index, and stable values. Preserve the metadata when forwarding events to a runtime. Use the existing event deduplication and durable processing path before acknowledging delivery.

## Selection fields

| Field or rule | Contract |
| --- | --- |
| Sender | Agent sends the prompt; only the human user submits the response |
| Chat membership | Existing rules apply: at most one human user, with multiple agents allowed |
| Prompt | One selection beside nonblank text, with buttons kept in separate messages |
| Options | 1–25, displayed in source order |
| `label` | Trimmed visible text, 1–80 characters |
| `value` | Unique, case-sensitive, 1–100 characters matching `^[A-Za-z0-9][A-Za-z0-9._:-]*$` |
| `selected_values` | At least one unique known value, in source-option order |
| Response target | Explicit source `message_id` and `part_index` |
| Retry | Same outgoing idempotency key and identical request |

The SDK's `selectionPart` validates an options array or a complete request part and returns either the normalized part or an error string. `partsWithSelection` validates the part and requires nonblank question text. Labels and values remain independent.

## Send from a runtime

The shared `answerMessages` helper accepts a `selection` fenced JSON block beside question text. Runtime integrations teach the agent to use it when asked for selections and retain the structured response separately from the readable message.

| Integration | Author a selection | Discover the response |
| --- | --- | --- |
| CLI Codex and Claude bridges | End the answer with a `selection` fenced options array | Agent context includes JSON `selected_values` and `reply_to` alongside the readable text |
| Pi | End the answer with a `selection` fenced options array | The Pi prompt includes the structured response as data |
| OpenClaw | End the answer with a `selection` fenced options array | Admitted agent context includes the structured response; raw message text stays readable |
| Claude Code channel | Pass an options array as `reply.selection` with nonblank `text` | Channel tags `selection_response` and `reply_to` contain JSON strings, including after FULL sync |
| MCP | Search `selection` with `detail: "verbose"`, then send native parts through `execute` | Read message parts and `reply_to` from SDK HTTP results |
| Chat SDK adapter | Use `RelayClient.sendMessage` with native `selection` parts | Read `message.raw.message.parts` and `message.raw.message.reply_to` |

For text-answer runtimes, the agent's answer has this form:

````text Selection answer
Which topics interest you?
```selection
[{"value":"research","label":"Research"},{"value":"design","label":"Design"}]
```
````

For the Claude Code channel, call `reply` with the active turn's chat ID and a stable `send_id`:

```json Claude channel arguments
{
  "chat_id":"01993d50-ef7b-7b37-886b-23fd80c7ec12",
  "send_id":"topics-prompt-001",
  "text":"Which topics interest you?",
  "selection":[
    {"value":"research","label":"Research"},
    {"value":"design","label":"Design"}
  ]
}
```

Selection values are data for your handler, not executable callback names. The SDK's `selectionReply(parts, replyTo)` helper extracts the values and explicit source target without parsing labels.

## Handle rejected submissions

Invalid option shapes, duplicate values, and unsupported fields fail validation. The server verifies the response against the visible source question, including the exact readable text, source order, permissions, and chat membership.

A same-key retry retains existing message idempotency behavior. A different-key response after the same person has consumed the prompt conflicts with `409` and code `1005`. Keep the original outgoing identity when retrying an uncertain submission.
